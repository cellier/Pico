# Telos / Pico 会议架构

更新：2026-10-14。

`MeetingSessionManager` 负责正式会议的生命周期、唯一会议编号、任务、正式转写、持久化和会后分析。

`MeetingAudioHub` 管理同一 Zoom 进程的一条采集流，向订阅者提供本机麦克风和对方音频。转写与 Pico 通过 lease 复用它；移除 Pico 不停止其他订阅者，最后一个订阅者结束才关闭采集。Pico 接管仍保留正式转写，结束会议关闭整个会话。

`BailianMeetingTranscription` 使用 `qwen-audio-3.1-asr-flash-streaming`，本机与对方各自有一条识别通道，以区分来源与时间。两条识别通道不是两份会议记录。停顿、重连、缺失区间和结束均应显示实际状态，不能静默换成本地模型。

`PicoRealtime` 使用 `qwen-audio-3.1-realtime-plus`，负责对话和记忆工具调用。它的输入文字用于对话，正式 transcript 由 ASR 保存。代理生成文字、被打断内容和故障日志附在同一场会议的 `picoRecords` 中，不能作为用户承诺的证据。

`PicoMeetingController` 负责输出音频、接管、演示提纲和播放进度。连接恢复不能重新从开场开始，也不能自动夺回用户主动接管后的控制权。

介绍只有一个推进方：控制器安排提纲，纯“继续”控制不再额外生成一段对话介绍。播放队列实际清空后才确认本机播放完成和安排下一段；部分播放须保留被打断状态。恢复指令带上一问答和已在本机播出的内容，要求一句相关过渡、避免重念定义和例子。控制事件不当作听众的行为加入对话历史；本机播放也不证明远端听到。

确认 Zoom 结束或进程消失时立即停止代理和同一份会议记录；暂时缺少可读控件则先静音暂停代理，保留转写防抖，不自动恢复发声；最小化或不可读的 unknown 不能当作结束。故障暂停不自动打开主人麦克风，主人须明确接管。

历史会议和任务保留原记录；新会话通过 `meetingID` 关联。导入 Pico 活动须幂等，不新增同场任务，不把生成内容混入正式 transcript。初始化失败且没有内容的记录可保存在诊断存储中，但不新增空白任务。

模型检查使用虚构知识和固定中英样本，不采集麦克风、不向会议播放。真实 Zoom 演练另行在用户授权的会议中进行。
